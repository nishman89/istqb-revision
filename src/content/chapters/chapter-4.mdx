## 4.1 Test Techniques Overview

### Test Techniques Overview

<SyllabusRef ref="4.1" />

A **test technique** is a systematic way of deciding **what to test** and **how to test it**. Instead of picking tests
at random, a technique helps you find a small but sufficient set of test cases that is likely to find defects.

- **Test analysis** - Techniques help decide *what* to test: the test conditions
- **Test design** - Techniques help decide *how* to test: the test cases
- **Building blocks** - Each technique defines its test conditions, coverage items and test data

<SyllabusText>

Test techniques support the tester in test analysis (what to test) and in test design (how to test). Test techniques help to develop a relatively small, but sufficient, set of test cases in a systematic way. Test techniques also help the tester to define test conditions, identify coverage items, and identify test data during the test analysis and design.

Further information on test techniques and their corresponding measures can be found in the ISO/IEC/IEEE 29119-4 standard, and in (Beizer 1990, Craig 2002, Copeland 2004, Koomen 2006, Jorgensen 2014, Ammann 2016, Forgacs 2019).

In this syllabus, test techniques are classified as black-box, white-box, and experience-based.

</SyllabusText>

### The Three Families of Techniques

<SyllabusRef ref="4.1" />

The syllabus groups test techniques into three families. Each one starts from a different source of information:

### Equivalence Partitioning

<SyllabusRef ref="4.2.1" />

<AtAGlance what="Split the possible values into groups (partitions) that the system should treat the same way, then test one value from each group." when="An input or output has a range or set of values that are handled alike, such as ages, prices or categories." why="Far fewer tests, while still covering every kind of value, including the invalid ones." />

#### How it works

1. **Pick a data element** to test. It can be an input, an output, a configuration value, an internal value, a time
   value or an interface parameter.
2. **Divide its values into partitions.** Every value in a partition should be processed the same way by the software.
3. **Mark each partition valid or invalid.** Valid values should be processed; invalid values should be ignored or rejected.
4. **Choose one test value from each partition.** If one value in a partition works, the others should too.

<Partitions caption="Example: a greeting chosen by the hour of the day — two partitions, so two tests (CTFL 4.2.1)" rows={[
  { label: 'Hour', segments: [{ text: '00:00 — 11:59  "Good morning"', pick: '09:00' }, { text: '12:00 — 23:59  "Good afternoon"', kind: 'valid', pick: '15:00' }] },
]} />

- **No overlaps, no gaps** - Partitions must not overlap, and none can be empty
- **Many shapes** - Partitions can be continuous or discrete, ordered or unordered, finite or infinite
- **Agree the definitions** - What counts as "valid" can vary between teams, so agree it up front

<SyllabusText>

Equivalence Partitioning (EP) divides data into partitions (known as equivalence partitions) based on the expectation that all the elements of a given partition are to be processed in the same way by the test object. The theory behind this technique is that if a test case, that tests one value from an equivalence partition, detects a defect, this defect should also be detected by test cases that test any other value from the same partition. Therefore, one test for each partition is sufficient.

Equivalence partitions can be identified for any data element related to the test object, including inputs, outputs, configuration items, internal values, time-related values, and interface parameters. The partitions may be continuous or discrete, ordered or unordered, finite or infinite. The partitions must not overlap and must be non-empty sets. For simple test objects EP can be easy, but in practice, understanding how the test object will treat different values is often complicated. Therefore, partitioning should be done with care.

A partition containing valid values is called a valid partition. A partition containing invalid values is called an invalid partition. The definitions of valid and invalid values may vary among teams and organizations. For example, valid values may be interpreted as those that should be processed by the test object or as those for which the specification defines their processing. Invalid values may be interpreted as those that should be ignored or rejected by the test object or as those for which no processing is defined in the test object specification.

</SyllabusText>

### Equivalence Partitioning Coverage

<SyllabusRef ref="4.2.1" />

In equivalence partitioning, the **coverage items are the partitions**, including the invalid ones.

<div class="formula"><span class="formula__label">EP coverage</span><span class="formula__expr">partitions exercised ÷ total partitions × 100%</span><span class="formula__note">100% means every partition, valid and invalid, has at least one test</span></div>

**More than one input?** Each test case can cover a partition from several sets at once. The simplest criterion is
**Each Choice coverage**: every partition from every set is exercised at least once. It does not try every
*combination* of partitions.

> **Watch out for:** partitions that are easy to miss, such as values below the minimum, above the maximum, or a range
> that wraps around midnight. Sketching the partitions on a line before you choose values helps.

<SyllabusText>

In EP, the coverage items are the equivalence partitions. To achieve 100% coverage with this technique, test cases must exercise all identified partitions (including invalid partitions) by covering each partition at least once. Coverage is measured as the number of partitions exercised by at least one test case, divided by the total number of identified partitions, and is expressed as a percentage.

Many test objects include multiple sets of partitions (e.g., test objects with more than one input parameter), which means that a test case will cover partitions from different sets of partitions. The simplest coverage criterion in the case of multiple sets of partitions is called Each Choice coverage (Ammann 2016). Each Choice coverage requires test cases to exercise each partition from each set of partitions at least once. Each Choice coverage does not take into account combinations of partitions.

</SyllabusText>

### Boundary Value Analysis

<SyllabusRef ref="4.2.2" />

<AtAGlance what="Test the values at the edges of ordered partitions, where developers most often make mistakes. It builds on equivalence partitioning." when="Values have a natural order, such as numbers, dates, lengths or times." why="Catches off-by-one mistakes, like writing < instead of <=, that one value per partition can miss." />

#### How it works

Boundary value analysis (BVA) only works for **ordered** partitions, such as numbers or dates. The **boundary values**
are the smallest and largest values in each partition. Developers are more likely to make mistakes at these edges, so a
boundary can end up implemented too high, too low, or not at all.

There are two versions, which differ in how many values you test around each boundary:

<BvaValues />

- **2-value BVA** - Test each boundary value and its closest neighbour in the next partition
- **3-value BVA** - Test each boundary value and *both* of its neighbours, so it is more thorough

<SyllabusText>

Boundary Value Analysis (BVA) is a technique based on exercising the boundaries of equivalence partitions. Therefore, BVA can only be used for ordered partitions. The minimum and maximum values of a partition are its boundary values. In the case of BVA, if two elements belong to the same partition, all elements between them must also belong to that partition.

BVA focuses on the boundary values of the partitions because developers are more likely to make errors with these boundary values. Typical defects found by BVA are located where implemented boundaries are misplaced to positions above or below their intended positions or are omitted altogether.

This syllabus covers two versions of BVA: 2-value and 3-value BVA. They differ in terms of coverage items per boundary that need to be exercised to achieve 100% coverage.

In 2-value BVA (Craig 2002, Myers 2011), for each boundary value there are two coverage items: this boundary value and its closest neighbor belonging to the adjacent partition. To achieve 100% coverage with 2-value BVA, test cases must exercise all coverage items, i.e., all identified boundary values. Coverage is measured as the number of boundary values that were exercised, divided by the total number of identified boundary values, and is expressed as a percentage.

In 3-value BVA (Koomen 2006, O'Regan 2019), for each boundary value there are three coverage items: this boundary value and both its neighbors. Therefore, in 3-value BVA some of the coverage items may not be boundary values. To achieve 100% coverage with 3-value BVA, test cases must exercise all coverage items, i.e., identified boundary values and their neighbors. Coverage is measured as the number of boundary values and their neighbors exercised, divided by the total number of identified boundary values and their neighbors, and is expressed as a percentage.

</SyllabusText>

### Boundary Value Analysis Coverage

<SyllabusRef ref="4.2.2" />

In BVA, the **coverage items are the boundary values** (and, for 3-value BVA, their neighbours too).

<div class="formula"><span class="formula__label">2-value BVA coverage</span><span class="formula__expr">boundary values exercised ÷ total boundary values × 100%</span></div>
<div class="formula"><span class="formula__label">3-value BVA coverage</span><span class="formula__expr">boundaries and neighbours exercised ÷ total boundaries and neighbours × 100%</span></div>

#### Why 3-value BVA finds more

Suppose a rule should say `if (x <= 10)`, but the developer wrote `if (x == 10)`:

| Test values | What happens | Result |
|---|---|---|
| 2-value BVA: **10** and **11** | Both behave correctly | Defect missed |
| 3-value BVA: **9**, **10** and **11** | 9 is now handled wrongly | **Defect found** |

<SyllabusText>

3-value BVA is more rigorous than 2-value BVA as it may detect defects overlooked by 2-value BVA. For example, if the decision "if (x ≤ 10) …" is incorrectly implemented as "if (x == 10) …", no test data derived from the 2-value BVA (x = 10, x = 11) can detect the defect. However, x = 9, derived from the 3-value BVA, is likely to detect it.

</SyllabusText>

### Decision Table Testing

<SyllabusRef ref="4.2.3" />

<AtAGlance what="List the combinations of conditions and the action each combination should trigger, in a table." when="A business rule depends on several conditions in combination, such as discounts, eligibility or approvals." why="Covers every combination systematically, and exposes gaps or contradictions in the requirements." />

#### How it works

A decision table lists the **conditions** at the top and the resulting **actions** underneath. Each **column** is one
**rule**: a unique combination of conditions, and the actions it should lead to.

| Symbol | Meaning |
|---|---|
| **T** / **F** | The condition is true / false |
| **–** | The condition doesn't matter for this rule |
| **N/A** | This combination is impossible (infeasible) |
| **X** | The action should happen |
| *blank* | The action should not happen |

Conditions are usually true or false (a **limited-entry** table), but they can also be ranges or partitions
(an **extended-entry** table).

#### Worked example: a printer troubleshooter

A support team diagnoses printer problems from three symptoms the customer describes. The table tells the adviser what to check:

<div class="table-wrap">

|   | Conditions / actions | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|---|
| Conditions | Printer does not print | T | T | T | T | F | F | F | F |
|   | A red light is flashing | T | T | F | F | T | T | F | F |
|   | Printer is unrecognised | T | F | T | F | T | F | T | F |
| Actions | Check the power cable |   |   | X |   |   |   |   |   |
|   | Check the printer-computer cable | X |   | X |   |   |   |   |   |
|   | Ensure printer software is installed | X |   | X |   | X |   | X |   |
|   | Check / replace ink | X | X |   |   | X | X |   |   |
|   | Check for paper jam |   | X |   | X |   |   |   |   |

</div>

<SyllabusText>

Decision tables are used for testing the implementation of system requirements that specify how different combinations of conditions result in different outcomes. Decision tables are an effective way of recording complex logic, such as business rules.

When creating decision tables, the conditions and the resulting actions of the system are defined. These form the rows of the table. Each column corresponds to a decision rule that defines a unique combination of conditions, along with the associated actions.

In limited-entry decision tables all the values of the conditions and actions (except for irrelevant or infeasible ones; see below) are shown as Boolean values (true or false). Alternatively, in extended-entry decision tables some or all the conditions and actions may also take on multiple values (e.g., ranges of numbers, equivalence partitions, discrete values).

</SyllabusText>

### Decision Table Coverage

<SyllabusRef ref="4.2.3" />

In decision table testing, the **coverage items are the feasible columns** (rules). To get there:

1. **Build the full table**, with every combination of conditions.
2. **Remove infeasible columns**, the combinations that can't happen.
3. **Minimise** by merging columns where some conditions don't affect the outcome. (Minimisation methods are outside the syllabus.)

<div class="formula"><span class="formula__label">Decision table coverage</span><span class="formula__expr">columns exercised ÷ feasible columns × 100%</span></div>

- **Strengths** - Finds every combination of conditions systematically, including easily overlooked ones · Exposes gaps and contradictions in the requirements
- **Limitations** - The number of rules grows exponentially with the number of conditions · Reduce it with a minimised table or a risk-based approach

<SyllabusText>

A full decision table has enough columns to cover every combination of conditions. The table can be simplified by deleting columns containing infeasible combinations of conditions. The table can also be minimized by merging columns, in which some conditions do not affect the outcome, into a single column. Decision table minimization algorithms are out of scope of this syllabus.

In decision table testing, the coverage items are the columns containing feasible combinations of conditions. To achieve 100% coverage with this technique, test cases must exercise all these columns. Coverage is measured as the number of exercised columns, divided by the total number of feasible columns, and is expressed as a percentage.

The strength of decision table testing is that it provides a systematic approach to identify all the combinations of conditions, some of which might otherwise be overlooked. It also helps to find any gaps or contradictions in the requirements. If there are many conditions, exercising all the decision rules may be time consuming, since the number of rules grows exponentially with the number of conditions. In such a case, to reduce the number of rules that need to be exercised, a minimized decision table or a risk-based approach may be used.

</SyllabusText>

### State Transition Testing

<SyllabusRef ref="4.2.4" />

<AtAGlance what="Model the system as states and the events that move it from one state to another, then test those transitions." when="Behaviour depends on what happened before, such as logins, orders, devices or workflows." why="Tests realistic sequences of events, including events that should not be allowed in a given state." />

#### How it works

A **state transition diagram** shows the **states** a system can be in, and the **transitions** between them. A
transition is triggered by an **event**, may only happen if a **guard condition** is true, and may cause an **action**:

<p class="label-syntax"><code>event [guard condition] / action</code></p>

#### Worked example: a video game

A game can be in one of four states: on the **main menu**, **running**, **paused** or **over**. The player's actions
are the events that move it from one state to another:

<GameStates />

Notice the arrow from **game running** to **game over**. Its event is *player loses a life*, but it only happens if
the **guard condition** `[lives = 1]` is true: losing a life with more lives left keeps the game running. (If a
transition also had an **action**, it would be written after a slash, for example *Player clicks "Quit" / save progress*.
This example keeps things simple and has none.)

The same model can be written as a **state table**: one row per state, one column per event. Filled cells are valid
transitions; **empty cells are invalid transitions**, which the diagram doesn't show. For example, you can't *pause*
from the main menu:

<div class="table-wrap">

| State / event | Start | Pause | Resume | Quit | Loses a life | Menu |
|---|---|---|---|---|---|---|
| **Main menu** | Game running | | | | | |
| **Game running** | | Game paused | | | Game over [lives = 1] | |
| **Game paused** | | | Game running | Main menu | | |
| **Game over** | | | | | | Main menu |

</div>

That gives **6 valid** transitions and **18 invalid** ones: 24 in total (4 states × 6 events). A **test case** is a
sequence of events, so one test case usually covers several transitions.

<SyllabusText>

A state transition diagram models the behavior of a system by showing its possible states and valid state transitions. A transition is initiated by an event, which may be additionally qualified by a guard condition. The transitions are assumed to be instantaneous and may sometimes result in the software taking action. The common transition labeling syntax is as follows: "event [guard condition] / action". Guard conditions and actions can be omitted if they do not exist or are irrelevant for the tester.

A state table is a model equivalent to a state transition diagram. Its rows represent states, and its columns represent events (together with guard conditions if they exist). Table entries (cells) represent transitions, and contain the target state, as well as the resulting actions, if defined. In contrast to the state transition diagram, the state table explicitly shows invalid transitions, which are represented by empty cells.

A test case based on a state transition diagram or state table is usually represented as a sequence of events, which results in a sequence of state changes (and actions, if needed). One test case may, and usually will, cover several transitions between states.

</SyllabusText>

### State Transition Coverage

<SyllabusRef ref="4.2.4" />

There are three coverage criteria for state transition testing, from weakest to strongest:

| Criterion | Coverage items | 100% means |
|---|---|---|
| **All states** | States | Every state is visited |
| **Valid transitions** (0-switch) | Valid transitions | Every valid transition is exercised |
| **All transitions** | Every cell in the state table | Every valid transition is exercised *and* every invalid one is attempted |

<div class="formula"><span class="formula__label">Coverage</span><span class="formula__expr">items exercised ÷ total items × 100%</span><span class="formula__note">for all transitions: (valid exercised + invalid attempted) ÷ all transitions</span></div>

- **All states** - The weakest: it can be achieved without exercising every transition
- **Valid transitions** - The most widely used · 100% guarantees 100% all-states coverage
- **All transitions** - The strongest · The minimum for mission and safety-critical software

> **Watch out for defect masking:** attempt only **one invalid transition per test case**, so one defect can't hide another.

<SyllabusText>

All states coverage is weaker than valid transitions coverage, because it can typically be achieved without exercising all the transitions. Valid transitions coverage is the most widely used coverage criterion. Achieving full valid transitions coverage guarantees full all states coverage. Achieving full all transitions coverage guarantees both full all states coverage and full valid transitions coverage and should be a minimum requirement for mission and safety-critical software.

</SyllabusText>

## 4.3 White-box Test Techniques

### White-box Test Techniques

<SyllabusRef ref="4.3" />

**White-box** techniques design tests from the **internal structure** of the code. The syllabus covers two, both based on
the code's control flow: **statement testing** and **branch testing**. More rigorous techniques exist, for example for
safety-critical systems, but they are outside the syllabus.

<SyllabusText>

Because of their popularity and simplicity, this section focuses on two code-related white-box test techniques: statement testing and branch testing. There are more rigorous techniques that are used in some safety-critical, mission-critical, or high-integrity environments to achieve more thorough code coverage. There are also white-box test techniques used in higher test levels (e.g., API testing), or using coverage not related to code (e.g., neuron coverage in neural network testing). These techniques are not discussed in this syllabus.

</SyllabusText>

### Statement Testing

<SyllabusRef ref="4.3.1" />

<AtAGlance what="A white-box technique: design tests so that every executable statement in the code runs at least once." when="The code is available, typically at the component (unit) level." why="Gives an objective measure of how much of the code has been exercised, and shows which code was never run." />

#### How it works

The **coverage items are the executable statements** in the code. You design tests until enough of them have been run.

<div class="formula"><span class="formula__label">Statement coverage</span><span class="formula__expr">statements exercised ÷ executable statements × 100%</span><span class="formula__note">100% means every executable statement has run at least once</span></div>

> **Watch out for:** running a statement doesn't guarantee its defect is found. A division by zero only fails when the
> divisor *is* zero, and 100% statement coverage may still leave some decision outcomes untested.

<SyllabusText>

In statement testing, the coverage items are executable statements. The aim is to design test cases that exercise statements in the code until an acceptable level of coverage is achieved. Coverage is measured as the number of statements exercised by the test cases divided by the total number of executable statements in the code, and is expressed as a percentage.

When 100% statement coverage is achieved, it ensures that all executable statements in the code have been exercised at least once. In particular, this means that each statement with a defect will be executed, which may cause a failure demonstrating the presence of the defect.

However, exercising a statement with a test case will not detect defects in all cases. For example, it may not detect defects that are data dependent (e.g., a division by zero that only fails when a denominator is set to zero). Also, 100% statement coverage does not ensure that all the decision logic has been tested as, for instance, it may not exercise all the branches (see chapter 4.3.2) in the code.

</SyllabusText>

### Branch Testing

<SyllabusRef ref="4.3.2" />

<AtAGlance what="A white-box technique: design tests so that every branch in the code is taken, including both outcomes of every decision." when="The code contains decisions, such as if-statements, loops and switch statements." why="Stronger than statement testing: 100% branch coverage always gives 100% statement coverage." />

#### How it works

A **branch** is a transfer of control between two points in the code's control flow graph. Branches are either
**conditional** (the outcome of a decision, such as each side of an `if`) or **unconditional** (straight-line code).
The **coverage items are the branches**.

<div class="formula"><span class="formula__label">Branch coverage</span><span class="formula__expr">branches exercised ÷ total branches × 100%</span><span class="formula__note">100% means every branch, conditional and unconditional, has been taken</span></div>

<ControlFlow />

<CoverageNest />

> **Watch out for:** 100% branch coverage still can't catch defects that only appear on one particular *path* through the code.

<SyllabusText>

A branch is a transfer of control between two nodes in the control flow graph, which shows the possible sequences in which source code statements are executed in the test object. Each transfer of control can be either unconditional (i.e., straight-line code) or conditional (i.e., a decision outcome). In branch testing the coverage items are branches and the aim is to design test cases to exercise branches in the code until an acceptable level of coverage is achieved. Coverage is measured as the number of branches exercised by the test cases divided by the total number of branches, and is expressed as a percentage.

When 100% branch coverage is achieved, all branches in the code, unconditional and conditional, are exercised by test cases. Conditional branches typically correspond to a true or false outcome from an "if...then" decision, an outcome from a switch/case statement, or a decision to exit or continue in a loop. However, exercising a branch with a test case will not detect defects in all cases. For example, it may not detect defects requiring the execution of a specific path in a code.

Branch coverage subsumes statement coverage. This means that any set of test cases achieving 100% branch coverage also achieves 100% statement coverage (but not vice versa).

</SyllabusText>

### The Value of White-box Testing

<SyllabusRef ref="4.3.3" />

Why bother looking inside the code, when black-box testing already checks the behaviour?

- **Strengths** - Considers the whole implementation, so it finds defects even when specifications are vague, outdated or incomplete · Gives an objective measure of code coverage, which black-box testing can't · Can be used statically, e.g. dry runs of code or pseudocode
- **Limitations** - Can't find defects of omission: requirements that were never implemented

<SyllabusText>

A fundamental strength that all white-box techniques share is that the entire software implementation is taken into account during testing, which facilitates defect detection even when the software specification is vague, outdated or incomplete. A corresponding weakness is that if the software does not implement one or more requirements, white-box testing may not detect the resulting defects of omission (Watson 1996).

White-box techniques can be used in static testing (e.g., during dry runs of code). They are well suited to reviewing code that is not yet ready for execution (Hetzel 1988), as well as pseudocode and other high-level or top-down logic which can be modeled with a control flow graph.

Performing only black-box testing does not provide a measure of actual code coverage. White-box coverage measures provide an objective measurement of coverage and provide the necessary information to allow additional tests to be generated to increase this coverage, and subsequently increase confidence in the code.

</SyllabusText>

## 4.4 Experience-based Test Techniques

### Experience-based Test Techniques

<SyllabusRef ref="4.4" />

**Experience-based** techniques rely on the **tester's knowledge, skills and intuition**. They find defects that the
formal black-box and white-box techniques can miss, so they work best **alongside** them. The syllabus covers three:
**error guessing**, **exploratory testing** and **checklist-based testing**.

### Error Guessing

<SyllabusRef ref="4.4.1" />

<AtAGlance what="Use knowledge and experience to anticipate likely errors, defects and failures, then design tests to expose them." when="Alongside the formal techniques, especially when the tester knows the product, the team or similar systems well." why="Finds defects that formal techniques can miss, quickly and cheaply." />

#### How it works

The tester anticipates the errors, defects and failures that are likely, based on what they know about:

- **The past** - How this application, or ones like it, have failed before
- **The developers** - The kinds of errors they tend to make
- **Similar systems** - Failures that have happened elsewhere

A methodical version is a **fault attack**: build a list of likely errors, defects and failures, then design tests to expose each one.

Common places to look:

<IconCards items={[
  { icon: '⌨️', title: 'Input', points: ['Correct input not accepted', 'Parameters wrong or missing'] },
  { icon: '🖨️', title: 'Output', points: ['Wrong format', 'Wrong result'] },
  { icon: '🔀', title: 'Logic', points: ['Missing cases', 'Wrong operator'] },
  { icon: '🧮', title: 'Computation', points: ['Wrong operand', 'Wrong result'] },
  { icon: '🔌', title: 'Interfaces', points: ['Parameter mismatch', 'Incompatible types'] },
  { icon: '🗃️', title: 'Data', points: ['Incorrect initialisation', 'Wrong type'] },
]} />

<SyllabusText>

Error guessing is a technique used to anticipate the occurrence of errors, defects, and failures, based on the tester's knowledge, including: how the application has worked in the past; the types of errors the developers tend to make and the types of defects that result from these errors; the types of failures that have occurred in other, similar applications.

Fault attacks are a methodical approach to the implementation of error guessing. This technique requires the tester to create or acquire a list of possible errors, defects and failures, and to design tests that will identify defects associated with the errors, expose the defects, or cause the failures. These lists can be built based on experience, defect and failure data, or from common knowledge about why software fails.

</SyllabusText>

### Exploratory Testing

<SyllabusRef ref="4.4.2" />

<AtAGlance what="Design, run and evaluate tests at the same time, while learning about the product, often in time-boxed sessions." when="Specifications are few or poor, time is short, or you want to complement the formal techniques." why="Fast feedback, and it finds unexpected problems that scripted tests would not look for." />

#### How it works

In exploratory testing, you **design, run and evaluate tests at the same time**, learning about the product as you go.
It is often organised as **session-based** testing:

<Flow caption="Session-based exploratory testing (CTFL 4.4.2)" steps={[
  { title: 'Test charter', sub: 'objectives to guide the session' }, { title: 'Time-boxed session', sub: 'design, run and learn at once' },
  { title: 'Session sheet', sub: 'steps and discoveries' }, { title: 'Debrief', sub: 'share results with stakeholders' },
]} />

- **Useful when** - Specifications are few or poor · Time is short · You want to complement the formal techniques
- **Works best when the tester** - Is experienced and knows the domain · Is curious, creative and analytical · Can bring in other techniques, such as equivalence partitioning

<SyllabusText>

In exploratory testing, tests are simultaneously designed, executed, and evaluated while the tester learns about the test object. The testing is used to learn more about the test object, to explore it more deeply with focused tests, and to create tests for untested areas.

Exploratory testing is sometimes conducted using session-based testing to structure the testing. In a session-based approach, exploratory testing is conducted within a defined time-box. The tester uses a test charter containing test objectives to guide the testing. The test session is usually followed by a debriefing that involves a discussion between the tester and stakeholders interested in the test results of the test session. In this approach test objectives may be treated as high-level test conditions. Coverage items are identified and exercised during the test session. The tester may use test session sheets to document the steps followed and the discoveries made.

Exploratory testing is useful when there are few or inadequate specifications or there is significant time pressure on the testing. Exploratory testing is also useful to complement other more formal test techniques. Exploratory testing will be more effective if the tester is experienced, has domain knowledge and has a high degree of essential skills, like analytical skills, curiosity and creativeness (see section 1.5.1). Exploratory testing can incorporate the use of other test techniques (e.g., equivalence partitioning).

</SyllabusText>

### Checklist-based Testing

<SyllabusRef ref="4.4.3" />

<AtAGlance what="Design and run tests to cover the items on a checklist, built from experience, standards or common failures." when="The same kinds of check need repeating, such as usability, security or coding standards." why="Consistent coverage of known risks, and the checklist can be reused and improved over time." />

#### How it works

The tester designs and runs tests to cover the items on a **checklist**. Checklists are built from experience, from
knowledge of what matters to users, and from common failures. Items are often phrased as questions, and each should be
checkable on its own.

<Resource kind="pdf" href="https://media.nngroup.com/media/articles/attachments/Heuristic_Summary1_A4_compressed.pdf" source="Nielsen Norman Group" title="Example checklist: the 10 usability heuristics" text="A widely used usability checklist — the kind of list a tester can work through in checklist-based testing" />

- **Keep checklists current** - Developers learn to avoid the errors on a checklist, so items wear out · Add new items as new defects are found
- **Keep them focused** - Long checklists get skipped, so keep them short and relevant

<SyllabusText>

In checklist-based testing, a tester designs, implements, and executes tests to cover test conditions from a checklist. Checklists can be built based on experience, knowledge about what is important for the user, or an understanding of why and how software fails. Checklists should not contain items that can be checked automatically, items better suited as entry/exit criteria, or items that are too general (Brykczynski 1999).

Checklist items are often phrased in the form of a question. It should be possible to check each item separately and directly. These items may refer to requirements, graphical interface properties, quality characteristics or other forms of test conditions. Checklists can be created to support various test types, including functional and non-functional testing (e.g., 10 heuristics for usability testing (Nielsen 1994)).

Some checklist entries may gradually become less effective over time because the developers will learn to avoid making the same errors. New entries may also need to be added to reflect newly found high severity defects. Therefore, checklists should be regularly updated based on defect analysis. However, care should be taken to avoid letting the checklist become too long (Gawande 2009).

In the absence of detailed test cases, checklist-based testing can provide guidelines and some degree of consistency for the testing. If the checklists are high-level, some variability in the actual testing is likely to occur, resulting in potentially greater coverage but less repeatability.

</SyllabusText>

## 4.5 Collaboration-based Test Approaches

### Collaboration-based Test Approaches

<SyllabusRef ref="4.5" />

The techniques so far focus on **finding** defects. Collaboration-based approaches also focus on **avoiding** them, by
getting business representatives, developers and testers to agree what is needed **before** it is built. The syllabus
covers **collaborative user story writing**, **acceptance criteria** and **acceptance test-driven development (ATDD)**.

### Collaborative User Story Writing

<SyllabusRef ref="4.5.1" />

<AtAGlance what="Business representatives, developers and testers write user stories together, so everyone shares the same picture of what is needed." when="Planning features in iterative and Agile development." why="Misunderstandings are caught before any code is written, which is the cheapest time to fix them." />

#### How it works

A **user story** describes a feature from the user's point of view, using the template
*As a* **[role]**, *I want* **[goal]**, *so that* **[business value]**. Every story has three parts, the **3 Cs**:

<Flow caption="The 3 Cs of a user story (CTFL 4.5.1)" steps={[
  { title: 'Card', sub: 'As a… I want… so that…' }, { title: 'Conversation', sub: 'how it will be used' }, { title: 'Confirmation', sub: 'the acceptance criteria' },
]} />

<Tiles cols={3} caption="Three perspectives create a shared vision — through brainstorming and mind mapping (CTFL 4.5.1)" tiles={[
  { title: 'Business', sub: 'what is valuable' }, { title: 'Development', sub: 'what is feasible' }, { title: 'Testing', sub: 'how we will know it works' },
]} />

A good story is **INVEST**:

- Independent
- Negotiable
- Valuable
- Estimable
- Small
- Testable

<SyllabusText>

A user story represents a feature that will be valuable to either a user or purchaser of a system or software. User stories have three critical aspects (Jeffries 2000), called together the "3 C's": Card — the medium describing a user story (e.g., an index card, an entry in an electronic board); Conversation — explains how the software will be used (can be documented or verbal); Confirmation — the acceptance criteria.

The most common format for a user story is "As a [role], I want [goal to be accomplished], so that I can [resulting business value for the role]", followed by the acceptance criteria.

Collaborative authorship of the user story can use techniques such as brainstorming and mind mapping. The collaboration allows the team to obtain a shared vision of what should be delivered, by taking into account three perspectives: business, development and testing.

Good user stories should be: Independent, Negotiable, Valuable, Estimable, Small and Testable (INVEST). If a stakeholder does not know how to test a user story, this may indicate that the user story is not clear enough, or that it does not reflect something valuable to them, or that the stakeholder just needs help in testing.

</SyllabusText>

<Exercise title="Spot the bad user story">

Which INVEST qualities does this story break, and how would you improve it?

> *As a user, I want the system to be fast and to have all the reporting features, and to integrate with the finance system.*

<div slot="answer">

- **Not Small or Estimable** - it bundles at least three pieces of work (speed, reporting, finance integration)
- **Not Testable** - "fast" and "all the reporting features" have no measurable acceptance criteria
- **Value unclear** - "a user" is vague and there's no "so that…", so the benefit isn't stated
- **Not Independent** - the parts depend on each other and can't be delivered separately

### Acceptance Criteria

<SyllabusRef ref="4.5.2" />

<AtAGlance what="The conditions a user story must meet to be accepted by the stakeholders." when="Writing or refining a user story, before it is built." why="They define the scope, give testers their test conditions, and make the story testable." />

#### What they are used for

- **Define the scope** - of the user story
- **Build consensus** - among the stakeholders
- **Describe scenarios** - both positive and negative
- **Plan and estimate** - as a basis for acceptance testing and estimation

#### Two common formats

- **Scenario-oriented** - Written as *Given / When / Then*, as used in BDD
- **Rule-oriented** - A bullet-point verification list, or a table of inputs and outputs

<SyllabusText>

Acceptance criteria for a user story are the conditions that an implementation of the user story must meet to be accepted by stakeholders. From this perspective, acceptance criteria may be viewed as the test conditions that should be exercised by the tests. Acceptance criteria are usually a result of the Conversation.

There are several ways to write acceptance criteria for a user story. The two most common formats are: scenario-oriented (e.g., Given/When/Then format used in BDD, see section 2.1.3) and rule-oriented (e.g., bullet point verification list, or tabulated form of input-output mapping). Most acceptance criteria can be documented in one of these two formats. However, the team may use another, custom format, as long as the acceptance criteria are well-defined and unambiguous.

</SyllabusText>

<Exercise title="Write the acceptance criteria">

Write two acceptance criteria — one positive, one negative — in **Given / When / Then** form for this story:

> *As a registered customer, I want to reset my password, so that I can get back into my account if I forget it.*

<div slot="answer">

There are many good answers. For example:

- **Positive:** *Given* I am a registered customer, *When* I request a password reset for my email address, *Then* I receive an email with a reset link that works for 24 hours.
- **Negative:** *Given* an email address that isn't registered, *When* I request a password reset, *Then* I see the same confirmation message (so the site doesn't reveal which emails are registered) and no email is sent.

Good criteria are clear, testable, and cover both what should and shouldn't happen.

</div>
</Exercise>

### Acceptance Test-Driven Development (ATDD)

<SyllabusRef ref="4.5.3" />

<AtAGlance what="Acceptance test-driven development: the team writes acceptance tests from the acceptance criteria before the code is written." when="Development is based on user stories with acceptance criteria." why="Builds a shared understanding of the requirement, and the tests become executable requirements." />

#### How it works

ATDD is a **test-first** approach: the test cases are written **before** the user story is implemented, by the team
together.

<Flow caption="Acceptance test-driven development — tests come before the code (CTFL 4.5.3)" steps={[
  { title: 'Specification workshop', sub: 'story and acceptance criteria' }, { title: 'Write test cases', sub: 'positive, negative, non-functional' },
  { title: 'Automate', sub: 'executable requirements' }, { title: 'Implement', sub: 'code until the tests pass' },
]} />

Write the test cases in this order:

1. **Positive tests:** confirm the correct behaviour, with no exceptions or errors
2. **Negative tests:** check what happens with invalid input or behaviour
3. **Non-functional tests:** for example performance or usability

- **Cover the whole story** - Every characteristic of the user story
- **Don't go beyond it** - Test only what the acceptance criteria describe
- **Use any technique** - The black-box techniques from 4.2 can help design the test cases

<SyllabusText>

ATDD is a test-first approach (see section 2.1.3). Test cases are created prior to implementing the user story. The test cases are created by team members with different perspectives, e.g., customers, developers, and testers (Adzic 2009). Test cases may be executed manually or automated.

The first step is a specification workshop where the user story and (if not yet defined) its acceptance criteria are analyzed, discussed, and written by the team members. Incompleteness, ambiguities, or defects in the user story are resolved during this process. The next step is to create the test cases. This can be done by the team as a whole or by the tester individually. The test cases are based on the acceptance criteria and can be seen as examples of how the software works. This will help the team implement the user story correctly.

Since examples and tests are the same, these terms are often used interchangeably. During the test design the test techniques described in sections 4.2, 4.3 and 4.4 may be applied.

Typically, the first test cases are positive, confirming the correct behavior without exceptions or error conditions, and comprising the sequence of activities executed if everything goes as expected. After the positive test cases are done, the team should perform negative testing. Finally, the team should cover non-functional quality characteristics as well (e.g., performance efficiency, usability). Test cases should be expressed in a way that is understandable for the stakeholders. Typically, test cases contain sentences in natural language involving the necessary preconditions (if any), the inputs, and the postconditions.

The test cases must cover all the characteristics of the user story and should not go beyond the story. However, the acceptance criteria may detail some of the issues described in the user story. In addition, no two test cases should describe the same characteristics of the user story.

When captured in a format supported by a test automation framework, the developers can automate the test cases by writing the supporting code as they implement the feature described by a user story. The acceptance tests then become executable requirements.

</SyllabusText>
